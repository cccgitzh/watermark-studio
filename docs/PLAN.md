# 项目规划：Watermark Studio

> 本文档记录需求分析、功能取舍、技术选型依据与交付路线。实现细节见 [README](../README.md)。

## 1. 背景与问题定义

参考项目 `cuijianzhuang/photo-watermark` 解决的问题很具体：**给身份证、驾照、护照等敏感证件加水印，且不能把图片传到任何服务器**。它的价值主张是「纯浏览器本地处理」，实现方式是单页原生 JS：

- `index.html`（8KB）负责结构，`css/styles.css`（24KB）负责样式，`js/script.js`（60KB）承载全部逻辑；
- 全局 `configInputSetting` 直接读取 DOM 节点 value，`drawText()` 在每次参数变化时全量重绘所有画布；
- 布局只有三种：平铺、单点（5 个固定位）、按数量均分；
- 导出靠 `canvas.toBlob` + `JSZip`；
- 部署走 GitHub Pages 静态托管 + Dockerfile。

### 1.1 原项目的具体局限

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | 全局函数 + DOM id 耦合，无模块边界 | 任何改动都可能影响其它路径，无法单测 |
| 2 | 一次只有一个文字水印 | 无法叠加 Logo、无法做「文字 + 角标」组合 |
| 3 | 单点仅 5 个固定位，无精确偏移 | 排版受限，无法微调 |
| 4 | 平铺只有一个「间距」参数 | 横纵间距不能独立控制，密度不可控 |
| 5 | 无描边 / 阴影 / 背景块 | 浅色底图上白字不可读 |
| 6 | 无导出格式与质量选择 | JPEG 重编码质量不可控，透明背景无法处理 |
| 7 | 批量渲染在主线程同步执行 | 大图批量处理时页面卡死，无进度、无法取消 |
| 8 | 无撤销、无方案复用 | 调错参数只能重来 |
| 9 | 无 EXIF 方向处理 | 手机竖拍照片导出后方向错误 |
| 10 | 无测试、无类型、无 CI | 回归风险高 |

## 2. 目标与非目标

### 目标
1. 保留「零上传」这一核心承诺，且可验证（无任何外部请求）；
2. 把水印从「一段文字」升级为「可复用的图层方案」，覆盖证件、图库、内部资料、社媒四类场景；
3. 批量处理 20~60 张 2~8MP 图片时，主线程不卡顿，有进度与取消；
4. 同一套参数在不同分辨率图片上视觉一致；
5. 代码可维护：纯逻辑可测、模块边界清晰、类型安全、CI 可验证；
6. 可一键部署到 EdgeOne，也支持任意静态托管与 Docker。

### 非目标（本期不做）
- 服务端存储、账号体系、云端方案同步（与隐私承诺冲突）；
- 视频水印、PDF 水印；
- 图形打码（矩形遮罩 / 马赛克）——列入路线图，避免首版范围失控；
- 移动端原生 App。

## 4. 技术选型

### 4.1 结论

| 层 | 选型 | 理由 | 放弃的方案 |
| --- | --- | --- | --- |
| 构建 | **Vite 5** | 静态产物、毫秒级 HMR、Worker 与动态 import 开箱支持、EdgeOne/Pages 均可直接识别 | Webpack（配置成本高）、无构建（无法用 TS/模块拆分） |
| 框架 | **React 18 + TypeScript(strict)** | 三栏编辑器有大量受控表单，声明式更新比手写 DOM diff 稳；TS 把「图层联合类型」的穷尽性检查交给编译器 | 原生 JS（原项目痛点）、Vue（团队栈无关，React 生态更适配 Canvas 编辑器）、Svelte（体积优势不足以抵消生态） |
| 状态 | **zustand 5** | 约 1KB、无 Provider 嵌套、可在 store 外 `getState()`（批量导出与快捷键需要） | Redux（样板过多）、Context（频繁重绘难控）、Jotai（撤销栈实现不直观） |
| 渲染 | **Canvas 2D + OffscreenCanvas + Web Worker** | 水印是像素合成，WebGL 收益低且实现成本高；Worker 解决批量卡顿 | WebGL/PixiJS（过度）、CSS 叠加（无法导出像素） |
| 样式 | **原生 CSS + 设计变量** | 三个 CSS 文件覆盖全部界面，无运行时、无原子类噪音，便于精确控制密度与主题 | Tailwind（产物可控性差）、CSS-in-JS（运行时开销与心智负担） |
| ZIP | **JSZip（按需加载）** | 成熟稳定；仅导出时加载，不进首屏 | fflate（更快但需要额外封装一层） |
| 测试 | **Vitest** | 与 Vite 同一套 transform，零额外配置 | Jest（需 babel/ts-jest 适配） |
| 部署 | **EdgeOne Makers / Pages** + Docker | 静态产物；EdgeOne 提供免费 CDN/HTTPS 与一键 CLI 部署 | 需要服务端渲染的方案（本项目无后端） |

### 4.2 关键取舍

**① 为什么不用 `canvas` 图层库（如 Fabric.js / Konva）？**
水印场景的图层结构极简（文字块 + 图片块，无自由变形、无多选编辑），引入编辑器框架会带来 50KB+ 体积与「所见即所得但导出不一致」的风险。自建 `renderer.ts` 只有约 300 行，且能保证预览与导出走同一条绘制路径。

**② 为什么参数都用比例而不是像素？**
用户在 800px 预览上把字号调到「好看」，导出 4000px 时必须同比放大。若存像素值，就得在每条绘制路径上乘缩放系数，且批量图片尺寸不一致时必然错位。改为「相对短边比例」后，同一配置天然适配所有分辨率——这是本项目与原项目在数值模型上的根本差异。

**③ Worker 渲染的边界**
`OffscreenCanvas` 在 Chrome/Edge/Safari 16.4+ 可用；自定义字体在 Worker 中的 `FontFace` 注册并不稳定。因此策略是：**默认 Worker，两条路径自动降级**——(a) 环境不支持 `OffscreenCanvas` → 主线程；(b) 使用了自定义字体 → 主线程（并降低并发为 1，保证字体已在 `document.fonts` 中生效）。降级不改变渲染结果，只影响速度，README 已披露。

**④ 打码为什么做成独立图层，而不是给文字加「背景遮罩」？**
文字层只能盖住自己的包围盒，形状受限且无法覆盖任意区域。证件号、住址这类需要遮挡的内容位置固定、形状自由，必须用「区域」表达。因此新增 `RedactLayer`：区域用相对画布的 0~1 比例存储，天然适配任意分辨率；渲染时直接操作画布像素（马赛克靠降采样 + 关闭平滑放大，模糊靠 `ctx.filter`），比叠加半透明色块更不可逆。

**⑤ 为什么打码必须先于水印绘制？**
若按图层顺序绘制，用户把水印层放在打码层之上时，文字会覆盖在打码区域上——虽然文字本身不含隐私，但视觉上会让人误以为该区域"被处理过"而实际像素仍可辨认的边界情况更容易发生。固定"打码永远先画"可以让「打码覆盖的像素一定被破坏」成为可推理的保证，代价是打码层不参与图层排序（UI 中已说明）。

**⑥ 为什么撤销栈放在 store 之外的模块变量？**
历史快照只服务于 `commit()`，不需要参与渲染。放在 store 状态里会让每次撤销都触发「历史数组」订阅者的重渲染；放在模块内 + 在 state 中只暴露 `pastCount/futureCount`，既保证按钮状态可响应，又避免无谓渲染。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 大图批量导致内存暴涨 | 移动端崩溃 | 单边 > 8192px 自动降采样；队列上限 60；并发 2 |
| 平铺参数极端（间距趋 0） | 绘制调用量爆炸、页面假死 | 间距下限 4px；锚点数量硬上限 10000 |
| 自定义字体在部分环境不可用 | 字体回退导致排版偏移 | 上传即校验 `FontFace.load()`，失败明确提示；不写入方案文件 |
| 部分浏览器不支持 `letterSpacing` | 字距失效 | 特性检测 + 逐字排版兜底 |
| 部分浏览器不支持 `ctx.filter` | 「模糊」静默失效，误以为已打码 | 特性检测；不支持时自动降级为马赛克，并在 UI 说明 |
| 断行规则与 Canvas 测量不一致 | 文字溢出容器 | 以 `measureText` 为准的贪心 + 悬挂标点；单测覆盖中英混排 |
| 部署子路径 404 | 白屏 | README 明确 `base` 配置；静态托管一律 SPA 回退 |
